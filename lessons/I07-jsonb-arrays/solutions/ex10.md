# I07 · ex10 📏 Lọc jsonb trên 32 triệu event: index có luôn nhanh hơn?

Query: số event có `utm_source = 'tiktok'` (≈ 3% số event). Hai cách viết:
`properties @> '{"utm_source": "tiktok"}'` (containment) và `properties->>'utm_source' = 'tiktok'`.

## Số đo thật (1 lần chạy; index tạo trong transaction rồi ROLLBACK)

| scale | không index | index biểu thức B-tree `((properties->>'utm_source'))` | index GIN `(properties jsonb_path_ops)` |
|---|---|---|---|
| s (32k event) | 5.6 ms | | |
| m (3.2M) | 366 ms (Parallel Seq Scan) | **223 ms** (Bitmap) · index 21 MB · tạo 1.0 s | **189 ms** (Bitmap) · index 14 MB · tạo 1.0 s |
| l (32M) | **3 727 ms** (Parallel Seq Scan) | **10 807 ms** (chậm hơn!) · 214 MB · tạo 28 s | **7 832 ms** (chậm hơn!) · 119 MB · tạo 27 s |

## Giải thích
- **Mỗi index chỉ phục vụ đúng kiểu toán tử của nó.** GIN `jsonb_path_ops` phục vụ `@>` (và `@?`, `@@`). B-tree trên biểu thức phục vụ đúng biểu thức `properties->>'utm_source' = …`. Viết điều kiện theo kiểu kia thì planner quay về Seq Scan (dòng thứ hai trong mỗi khối EXPLAIN).
- **Ở `m`, index nhanh hơn khoảng 1.6–2 lần.** Chưa nhiều, vì kết quả là 100k dòng (3%), rải khắp bảng.
- **Ở `l`, index còn CHẬM HƠN Seq Scan 2–3 lần.** Kết quả có ~1M dòng nằm rải trên gần như mọi page. Bitmap vượt `work_mem` (4MB) nên chuyển sang *lossy*: Postgres chỉ nhớ "page nào có dòng khớp" và phải kiểm tra lại cả page (*Rows Removed by Index Recheck: 8.3 triệu*). Đọc theo kiểu bitmap còn kém song song hóa hơn Seq Scan.
  Planner vẫn chọn index vì ước lượng chi phí chưa tính hết hiệu ứng lossy. P03/P04 sẽ học cách đọc và sửa những ca này.
- **Bài học:**
  1. Index giúp khi điều kiện **chọn lọc** (ít dòng, tập trung ở ít page). 3% của 32 triệu vẫn là 1 triệu dòng.
  2. Index tốn chỗ (120–214 MB) và mất 27–28 s để tạo ở `l`. Nó còn làm chậm mọi lần ghi (P10b).
  3. Chọn loại index theo **cách bạn viết điều kiện**. Nếu luôn lọc một key cố định, B-tree biểu thức (hoặc tách key đó thành cột thật) đơn giản hơn GIN. GIN hợp với điều kiện linh hoạt trên nhiều key.
  4. Luôn đo ở quy mô thật: kết luận ở `m` ("index nhanh hơn") bị đảo ngược ở `l`.
