# O05 · ex05 — Checkpoint dồn dập

Môi trường: container tạm `postgres:18` (mặc định: `shared_buffers=128MB`, `max_wal_size=1GB`, `checkpoint_timeout=5min`), `pgbench -i -s 20`, mỗi lần `pgbench -c8 -j4 -T60` (TPC-B, có ghi).

```bash
docker exec o05-pg psql -U postgres -c "ALTER SYSTEM SET max_wal_size='64MB'" -c "ALTER SYSTEM SET log_checkpoints=on" -c "SELECT pg_reload_conf()"
docker exec o05-pg psql -U postgres -c "CHECKPOINT" -c "SELECT pg_stat_reset_shared('checkpointer')"
docker exec o05-pg pgbench -c8 -j4 -T60 -U postgres postgres
docker exec o05-pg psql -U postgres -c "SELECT num_timed, num_requested, round(write_time) AS write_ms, buffers_written FROM pg_stat_checkpointer"
```

## Kết quả
| `max_wal_size` | tps | `num_timed` | `num_requested` | `write_time` | `buffers_written` |
|---|---|---|---|---|---|
| 64MB | **1 040** | 0 | **21** | 52 160 ms | 79 274 (≈ 620 MB) |
| 4GB | **1 277** | 0 | 0 | 0 | 0 |

## Đọc kết quả
- **`num_requested = 21` trong 60 giây** (mỗi ≈ 3 s một lần) là dấu hiệu kinh điển của `max_wal_size` quá nhỏ: WAL đầy trước khi hết `checkpoint_timeout` nên checkpoint bị ép chạy. Mỗi checkpoint ghi mọi trang bẩn xuống đĩa; sau mỗi checkpoint, lần sửa đầu tiên của mỗi trang lại ghi **cả trang** vào WAL (`full_page_writes`), nên WAL phình thêm và checkpoint tới sớm hơn: một vòng luẩn quẩn.
- Chậm đi **19%** (1 040 so với 1 277) trong 60 s. Với `log_checkpoints = on`, checkpoint bị ép bởi WAL được ghi là `checkpoint starting: wal` (thay vì `time`); tôi bật log này nhưng không đọc lại nó trong lần đo, nên đây là hành vi chuẩn chứ không phải điều đã quan sát.
- Cách chẩn đoán trên hệ thống thật: `num_requested` cao so với `num_timed`, hoặc log có `checkpoints are occurring too frequently` (bật `log_checkpoints = on`).

## Phép đo này có công bằng cho 4GB không?
**Không hoàn toàn.** 60 giây ngắn hơn `checkpoint_timeout` (5 phút), nên phía 4GB chưa phải trả checkpoint nào: số 1 277 là cận trên. Để so sánh công bằng cần chạy ≥ 10–15 phút để có vài checkpoint "timed" ở cả hai phía; chênh lệch dài hạn sẽ nhỏ hơn 19%. (Tôi chưa chạy bản dài này.)

## Cái giá của `max_wal_size` lớn
1. **Phục hồi sau crash lâu hơn**: phải replay nhiều WAL hơn kể từ checkpoint gần nhất (thời gian phục hồi tỉ lệ với lượng WAL sau checkpoint cuối). Tôi chưa đo thời gian phục hồi cho hai cấu hình này.
2. Tốn đĩa cho WAL (tới ≈ `max_wal_size`, cộng slot replication/archive giữ lại).
3. Mỗi lần checkpoint ghi nhiều trang bẩn hơn một lúc: `checkpoint_completion_target` (mặc định 0,9) trải việc ghi ra trong 90% khoảng giữa hai checkpoint để tránh giật.

Quy tắc: đặt `max_wal_size` đủ lớn để checkpoint chủ yếu là "timed" ở giờ cao điểm, rồi cân với thời gian phục hồi chấp nhận được.
