# O04 · ex06 🔴 "Cao điểm là app báo lỗi kết nối"

**Cảnh báo an toàn.** Làm bài này trên một Postgres **tạm** với `max_connections` nhỏ, đừng làm trên DB đang dùng chung. Khi tôi dồn khoảng 100 kết nối `psql` cùng lúc vào sát giới hạn 100 của `sql-practice-pg`, server đã tự restart một lần (`untracked child process … exited with exit code 2` → `terminating any other active server processes` → crash recovery, ≈ 5 s, không mất dữ liệu). Chưa tìm ra nguyên nhân gốc; coi đây là lý do để thí nghiệm giới hạn kết nối trong một container riêng.

```bash
docker run -d --name o04-lowconn -e POSTGRES_PASSWORD=postgres postgres:18 -c max_connections=20 -c superuser_reserved_connections=3
# dọn: docker rm -f o04-lowconn
```
`max_connections = 20`, dành riêng 3 → ứng dụng dùng được **17**.

## Tái hiện
14 kết nối `idle` của `api` (pool ứng dụng giữ mà không dùng) + 3 kết nối `idle in transaction` của `worker`:
```
 application_name |        state        | count
 api              | idle                |    14
 worker           | idle in transaction |     3
```
Ứng dụng xin kết nối thứ 18:
```
FATAL:  remaining connection slots are reserved for roles with the SUPERUSER attribute
```
(Hai thông báo khác nhau tùy chạm tới đâu: `sorry, too many clients already` khi **mọi** chỗ kể cả phần dành riêng đã hết; `remaining connection slots are reserved…` khi chỉ còn phần dành riêng. Superuser vẫn vào được để điều tra — đó là lý do phần dành riêng tồn tại.)

CPU server 83% rảnh: **hết kết nối không có nghĩa là quá tải**; chúng bị chiếm bởi kết nối không làm gì.

## Điều tra
```sql
SELECT application_name, state, count(*)
FROM pg_stat_activity WHERE backend_type = 'client backend' GROUP BY 1, 2 ORDER BY 3 DESC;
SELECT application_name, state, round(extract(epoch FROM now() - state_change)) AS idle_s
FROM pg_stat_activity WHERE state LIKE 'idle in tr%';       -- 4 s trong thí nghiệm
```
Hai thủ phạm: (1) `api` giữ 14 kết nối `idle`: tổng pool của các bản chạy lớn hơn nhu cầu; (2) `worker` có 3 `idle in transaction`: bug "quên COMMIT" (giữ khóa, chặn VACUUM).

## Các cách chữa, xếp theo hiệu quả / rủi ro
| # | Cách | Hiệu quả | Rủi ro / giá |
|---|---|---|---|
| 1 | **Cắt `idle in transaction`** (khẩn cấp) `pg_terminate_backend` | thả ngay 3 chỗ (đã chạy: `3`, app vào lại được) | giao dịch dở bị rollback; phải sửa bug quên COMMIT, không thì lặp lại |
| 2 | **Timeout ở cấp role** `idle_in_transaction_session_timeout`, `idle_session_timeout` | phòng ngừa lâu dài, không sửa app | cắt nhầm kết nối hợp lệ nếu đặt quá ngắn; app phải tự nối lại được |
| 3 | **Giảm tổng pool ở ứng dụng** (bản chạy × cỡ pool ≤ ngân sách, ex02) | triệt gốc, miễn phí | cần đổi cấu hình và triển khai lại |
| 4 | **PgBouncer** transaction mode | ôm nhiều client với ít kết nối server (ex05) | thêm một thành phần; bẫy transaction mode (ex07); −30% khi ít client |
| 5 | Tăng `max_connections` | đổi lấy bộ nhớ chia sẻ, tranh chấp CPU; thông lượng **không** tăng (README mục 3) | cần restart; chỉ là hoãn vấn đề |

Kết quả `idle_in_transaction_session_timeout = 2s`, `idle_session_timeout = 4s` đặt cho role ứng dụng (`ALTER ROLE … SET …`):
```
FATAL:  terminating connection due to idle-in-transaction timeout
FATAL:  terminating connection due to idle-session timeout
```

## Quy trình
1. Phân loại kết nối (state, application_name). 2. Cắt `idle in transaction` trước, vì vừa chiếm chỗ vừa chặn VACUUM. 3. Tính ngân sách (ex02) rồi giảm pool. 4. Đặt timeout phòng ngừa. 5. Chỉ khi vẫn thiếu mới tới PgBouncer rồi mới nghĩ đến `max_connections`. Nhớ `application_name` ở mọi ứng dụng để lần sau biết ngay ai chiếm.
