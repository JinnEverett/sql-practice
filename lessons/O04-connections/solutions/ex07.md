# O04 · ex07 🔴 "Bật PgBouncer xong thì app lỗi lung tung"

Cấu hình `pgbouncer/pgbouncer.ini` có sẵn hai DB nhỏ để tái hiện: `o04_one` (`pool_size = 1`) và `o04_two` (`pool_size = 2`), cả hai ở `pool_mode = transaction`. Mỗi lệnh `psql` bên dưới là **một client mới**. (Với một client duy nhất và pool rảnh, PgBouncer hay trả lại đúng kết nối server cũ nên lỗi *không* lộ ra: bẫy chỉ xuất hiện khi nhiều client chen nhau, tức là đúng lúc có tải thật.)

## Bẫy 1 — `SET` rò rỉ: "timeout ở request không liên quan"
```
A:  SET statement_timeout = '1234ms';      -- pid server 5989
B:  SHOW statement_timeout;                -- pid server 5989, statement_timeout = 1234ms   ← B thừa hưởng giá trị của A
```
`SET` (cấp session) dính vào **kết nối server**, không dính vào client. Request không liên quan chạy sau đó nhận timeout 1,2 s.
**Sửa:** `SET LOCAL` trong transaction (hết hiệu lực khi COMMIT; đã kiểm: `in_tx = 9s`, sau COMMIT quay về giá trị cũ), hoặc đặt ở cấp role/DB (`ALTER ROLE … SET statement_timeout = …`), hoặc tham số trong connection string nếu pooler cho phép.

## Bẫy 2 — advisory lock cấp session: "job nền cạnh tranh lock lạ"
```
A:  SELECT pg_try_advisory_lock(7);        -- true, giữ trên server conn 1
B:  SELECT count(*) FROM pg_locks WHERE locktype='advisory' AND pid = pg_backend_pid();   -- 1  ← B đang đứng trên kết nối giữ khóa
```
Khóa thuộc về kết nối server. Client A tưởng mình đã giữ khóa (nhưng giao dịch sau của A có thể rơi sang kết nối khác, không có khóa); client B vô tình đứng trên kết nối đang giữ khóa của A. Kết quả: hai job chạy chồng nhau, hoặc job bị kẹt chờ một khóa mà không ai "sở hữu" hợp lệ.
**Sửa:** `pg_advisory_xact_lock(key)` (tự nhả khi kết thúc transaction, đúng ngữ nghĩa cho transaction pooling) và bao toàn bộ công việc trong một transaction.

## Bẫy 3 — `PREPARE` ở mức SQL: `prepared statement "q1" does not exist`
Pool 2 kết nối; `PREPARE q1 AS SELECT 1` chạy trên server pid 5990. Giữ cả hai kết nối server bận bằng hai transaction dài (`pg_sleep(4)`), rồi 4 client chạy `EXECUTE q1`:
```
lần 1: ERROR:  prepared statement "q1" does not exist
lần 2: ERROR:  prepared statement "q1" does not exist
lần 3: ERROR:  prepared statement "q1" does not exist
lần 4: ERROR:  prepared statement "q1" does not exist
```
(Cả 4 lỗi cũng hiện trong log server: `ERROR: prepared statement "q1" does not exist`.) Prepared statement thuộc về kết nối server; sang kết nối khác thì không thấy.
**Sửa, không phải quay về session mode:**
- Dùng prepared statement **ở mức giao thức** (driver gửi Parse/Bind/Execute): PgBouncer ≥ 1.21 theo dõi và nhân bản chúng qua `max_prepared_statements` (cấu hình đang chạy: `SHOW CONFIG` → `max_prepared_statements = 200`). Tăng giá trị này nếu ứng dụng có nhiều câu khác nhau.
- Hoặc tắt prepare ở driver (vd. tuỳ chọn tương ứng của ORM) và chấp nhận re-parse.
- Không dùng `PREPARE`/`EXECUTE` SQL thủ công qua pooler.

## Còn lại (không đo; theo tài liệu PgBouncer)
`LISTEN/NOTIFY`, bảng `TEMP`, `DECLARE … WITH HOLD`, `SET SESSION AUTHORIZATION` cũng gắn với session: dùng một kết nối riêng không qua pooler hoặc `session` mode cho các tính năng đó.

## Danh sách kiểm trước khi bật transaction mode
1. `grep` mã nguồn tìm `SET `, `pg_advisory_lock`, `PREPARE`, `LISTEN`, `CREATE TEMP`. 2. Chạy bộ test qua PgBouncer với `pool_size` nhỏ (1–2) và nhiều client xen kẽ: đó mới là cấu hình lộ lỗi. 3. Đặt tham số bằng `SET LOCAL` hoặc cấp role. 4. Giữ một đường kết nối riêng (session mode hoặc trực tiếp) cho job cần tính năng session.
