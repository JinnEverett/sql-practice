# O06 · ex06 🔴 "Primary chết lúc 3 giờ sáng"

Cặp primary/replica của ex04, bảng `ryw(id serial primary key, v text)`. Bất đồng bộ, replica đã bắt kịp lúc primary dừng.

## 1. Primary dừng, promote replica
```bash
docker exec o06-primary psql -U postgres -c "insert into ryw(v) values ('trước-sự-cố')"
docker stop o06-primary                                            # "primary chết"
docker exec o06-replica psql -U postgres -c "select pg_promote(wait => true)"      # t, ≈ 545 ms gồm chi phí docker exec
docker exec o06-replica psql -U postgres -c "select pg_is_in_recovery()"           # f
docker exec o06-replica psql -U postgres -c "insert into ryw(v) values ('sau-failover') returning id"   # 1024 (xem ghi chú)
```
- **Timeline** đổi 1 → 2. Đọc đáng tin cậy từ tên file WAL: `left(pg_walfile_name(pg_current_wal_lsn()), 8)` → `00000002` (còn `pg_control_checkpoint().timeline_id` vẫn là `1` cho tới checkpoint kế tiếp).
- **ID nhảy** từ 1002 lên 1024: sequence được ghi WAL trước một đoạn giá trị (tối đa 32), nên sau failover có khoảng trống. Bình thường, đừng giả định ID liên tục.

## 2. Primary cũ "tự bật lại" → split-brain
```bash
docker start o06-primary
docker exec o06-primary psql -U postgres -c "select pg_is_in_recovery()"        # f  ← vẫn tin mình là primary, timeline 1
docker exec o06-primary psql -U postgres -c "insert into ryw(v) values ('ghi-vào-primary-cũ') returning id"   # 1003
```
Dữ liệu hai nơi (`id >= 1000`):
```
primary cũ : 1000:x, 1001:vừa-ghi, 1002:trước-sự-cố, 1003:ghi-vào-primary-cũ
primary mới: 1000:x, 1001:vừa-ghi, 1002:trước-sự-cố, 1024:sau-failover
```
Hai bên **cùng nhận ghi và đã rẽ nhánh**. Không có "bên nào đúng" khi hợp nhất. Đây là lý do HA cần **fencing**: bảo đảm primary cũ không thể nhận ghi (tắt máy/STONITH, rút khỏi proxy/VIP, hoặc cơ chế khóa lãnh đạo tự hạ nó xuống).

## 3. Đưa primary cũ về làm replica
```bash
docker stop o06-primary                                   # phải dừng sạch
docker run --name o06-rewind --network o06-net --volumes-from o06-primary postgres:18 \
  gosu postgres pg_rewind --target-pgdata=/var/lib/postgresql/18/docker \
  --source-server="host=o06-replica port=5432 user=postgres password=postgres dbname=postgres" \
  --write-recovery-conf --progress
```
Kết quả:
```
pg_rewind: servers diverged at WAL location 0/B578A90 on timeline 1
pg_rewind: need to copy 179 MB (total source directory size is 351 MB)
pg_rewind: Done!
```
`pg_rewind` chỉ chép phần đã thay đổi từ điểm rẽ nhánh, nhanh hơn dựng lại bằng `pg_basebackup` (351 MB ở đây là nhỏ). Yêu cầu: data checksums hoặc `wal_log_hints = on` (PG18 bật checksums mặc định), `full_page_writes = on`, primary cũ tắt sạch. **Dòng `1003:ghi-vào-primary-cũ` bị loại bỏ**: dữ liệu ghi nhầm ở primary cũ sau failover bị mất, nên ứng dụng phải biết (ghi log) rằng có khoảng thời gian ghi vào nhầm nơi.

## 4. Hai bẫy khi rejoin (đã gặp thật)
Khởi động lại primary cũ (giờ là standby) nhưng nó không stream:
1. **`pg_hba.conf` của primary mới**: `FATAL: no pg_hba.conf entry for replication connection from host "172.27.0.2", user "…"`. `pg_rewind -R` ghi `primary_conninfo` bằng đúng user của `--source-server` (`postgres`), nhưng primary mới chỉ cho `replicator` kết nối replication. Sửa: thêm `host replication postgres all scram-sha-256` và reload (hoặc đổi `primary_conninfo` sang `replicator`).
2. **Replication slot không được sao chép**: `FATAL: could not start WAL streaming: ERROR: replication slot "replica1" does not exist`. `primary_slot_name = 'replica1'` đi theo dữ liệu, nhưng slot nằm ở primary cũ. Sửa: `SELECT pg_create_physical_replication_slot('replica1')` trên primary mới.

Sau hai sửa đổi:
```
172.27.0.2 | streaming | async | 0 bytes          (pg_stat_replication trên primary mới)
dữ liệu trên standby cũ: x,vừa-ghi,trước-sự-cố,sau-failover,sau-rejoin
```

## 5. Patroni làm hộ những gì (khái niệm, không dựng trong bài)
- **Phát hiện & bầu chọn:** các node cạnh tranh một *leader key* (có TTL) trong kho phân tán (etcd/Consul/ZooKeeper). Node giữ được khóa là primary; mất khóa là tự hạ xuống replica (một dạng fencing mềm), và watchdog có thể tự khởi động lại node bị "treo".
- **Chọn replica để promote** theo lag/ưu tiên; **cấu hình lại** các replica còn lại theo primary mới.
- **Rejoin:** tự chạy `pg_rewind` (hoặc dựng lại) cho primary cũ, quản lý slot.
- **Định tuyến:** cung cấp endpoint kiểm tra vai trò (REST) cho HAProxy/VIP/DNS.
- Việc phải tự lo: kho phân tán (cần đa số), backup/PITR (O02), quyết định đồng bộ/bất đồng bộ (mất dữ liệu vs mất khả dụng), và kiểm tra failover định kỳ.

## Danh sách việc cần có để chu trình trên chạy
`pg_hba` cho replication (cả user cho `pg_rewind -R`) · replication slot trên primary mới · data checksums hoặc `wal_log_hints` · dừng sạch primary cũ · fencing · cập nhật điểm vào cho ứng dụng · ghi nhận mọi giao dịch có thể mất (async).

## Dọn
`docker rm -f -v o06-primary o06-replica o06-rewind`, `docker network rm o06-net`.
