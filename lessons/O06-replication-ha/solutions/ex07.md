# O06 · ex07 — Logical replication

Hai instance `postgres:18` trong cùng mạng Docker: publisher `o06-pub` khởi động với `-c wal_level=logical` (đổi tham số này cần restart), subscriber `o06-sub` để mặc định.
```bash
docker run -d --name o06-pub --network o06-net --shm-size=128m -e POSTGRES_PASSWORD=postgres postgres:18 -c wal_level=logical
docker run -d --name o06-sub --network o06-net --shm-size=128m -e POSTGRES_PASSWORD=postgres postgres:18
```

## 1. Dựng
```sql
-- publisher
CREATE TABLE items (id serial PRIMARY KEY, name text, qty int);
CREATE TABLE items_nopk (a int, b text);                      -- cố ý không có khóa
INSERT INTO items(name, qty) SELECT 'i'||g, g FROM generate_series(1,100) g;
INSERT INTO items_nopk SELECT g, 'r'||g FROM generate_series(1,5) g;
CREATE PUBLICATION p FOR TABLE items, items_nopk;
-- subscriber: bảng phải tạo sẵn (logical KHÔNG sao chép cấu trúc)
CREATE TABLE items (id serial PRIMARY KEY, name text, qty int);
CREATE TABLE items_nopk (a int, b text);
CREATE SUBSCRIPTION s CONNECTION 'host=o06-pub port=5432 user=postgres password=postgres dbname=postgres' PUBLICATION p;
-- NOTICE: created replication slot "s" on publisher
```
Sau vài giây: subscriber có `items = 100`, `items_nopk = 5` (đồng bộ ban đầu), rồi mỗi `INSERT` ở publisher xuất hiện ở subscriber (101 sau khi thêm một dòng).

## 2. Từng bẫy, đã tái hiện

### Bẫy 1 — bảng không có khóa / replica identity
```sql
-- publisher
UPDATE items_nopk SET b = 'x' WHERE a = 1;
-- ERROR:  cannot update table "items_nopk" because it does not have a replica identity and publishes updates
-- HINT:   To enable updating the table, set REPLICA IDENTITY using ALTER TABLE.
```
`INSERT` thì được, nhưng `UPDATE`/`DELETE` cần cách nhận diện dòng ở phía nhận. Sửa: thêm khóa chính, hoặc `ALTER TABLE items_nopk REPLICA IDENTITY FULL` (đắt: WAL ghi cả dòng cũ).

### Bẫy 2 — sequence không được sao chép
```
publisher: nextval('items_id_seq') = 102
subscriber: nextval('items_id_seq') = 1
```
Dữ liệu `id` đến từ publisher, nhưng sequence ở subscriber đứng yên. Nếu một ngày subscriber trở thành nơi ghi (cutover), `nextval` trả `1` và đụng khóa. Trước khi chuyển, phải `setval` sequence ở subscriber theo `max(id)`.

### Bẫy 3 — DDL không được sao chép, subscription kẹt
```sql
-- publisher
ALTER TABLE items ADD COLUMN note text;
INSERT INTO items(name, qty, note) VALUES ('có-note', 2, 'n');
```
Subscriber vẫn `items = 101` và log báo:
```
ERROR:  logical replication target relation "public.items" is missing replicated column: "note"
```
Apply worker thoát và khởi động lại liên tục; **không có dữ liệu nào sau điểm đó được áp dụng** (kể cả các bảng khác trong cùng subscription).

### Bẫy 4 — subscription kẹt làm publisher giữ WAL
Trong lúc kẹt, nạp 300 000 dòng vào `items_nopk` ở publisher:
```sql
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_held,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)) AS not_confirmed
FROM pg_replication_slots WHERE slot_name = 's';
--  46 MB | 46 MB
```
Slot không cho publisher xóa WAL mà subscriber chưa xác nhận. Một subscription chết lâu → **đĩa publisher đầy**. Theo dõi `pg_replication_slots` và đặt `max_slot_wal_keep_size`.

Sửa bẫy 3: thêm cột ở subscriber (`ALTER TABLE items ADD COLUMN note text`). Sau vài giây subscriber đuổi kịp: `items` có 102 dòng (1 dòng có `note`), `items_nopk` có 300 005 dòng. Quy tắc áp dụng DDL cho logical: thêm cột ở **subscriber trước**, rồi ở publisher.

### Bẫy 5 — ghi ở subscriber gây xung đột
Subscriber vẫn **ghi được** (khác replica vật lý). Chèn `id = 9999` ở subscriber, rồi chèn cùng `id` ở publisher:
```
ERROR:  conflict detected on relation "public.items": conflict=insert_exists
DETAIL: Key already exists in unique index "items_pkey", modified in transaction 781.
```
Apply worker thoát với mã 1 và khởi động lại sau ≈ 5 s, lặp lại mãi; replication **đứng** và slot lại giữ WAL (46 MB) cho đến khi con người gỡ xung đột (xóa dòng thừa ở subscriber hoặc bỏ qua giao dịch). Logical replication **không tự giải quyết xung đột**. Thường giữ bảng nhận ở chế độ chỉ đọc đối với ứng dụng.

## 3. Khi nào chọn logical thay vì streaming
| Dùng logical khi | Dùng streaming khi |
|---|---|
| nâng cấp major version/đổi nền tảng ít downtime | HA, failover |
| chỉ cần một số bảng (hoặc cột/dòng) ở nơi khác | cần bản sao nguyên cụm, cả DDL và sequence |
| tích hợp/CDC sang hệ thống khác, replica cần ghi thêm bảng riêng | mở rộng đọc đơn giản nhất |

Cái giá của logical: tự quản DDL và sequence, cần khóa/replica identity, xung đột phải xử lý bằng tay, WAL bị giữ khi chậm.

## Dọn
`docker rm -f -v o06-pub o06-sub`, `docker network rm o06-net`.
