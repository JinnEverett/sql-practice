# P08 · ex06: đọc log deadlock

Log đề bài là log thật do chính bài ex03 (bản ngây thơ) sinh ra trên Postgres 18.6:

```
ERROR:  deadlock detected
DETAIL:  Process 14233 waits for ShareLock on transaction 515922; blocked by process 14227.
	Process 14227 waits for ShareLock on transaction 515923; blocked by process 14233.
	Process 14233: UPDATE p08.acct SET balance = balance + 10 WHERE id = 1;
	Process 14227: UPDATE p08.acct SET balance = balance + 10 WHERE id = 2;
CONTEXT:  while updating tuple (0,1) in relation "acct"
```

## Trả lời
1. **Vòng chờ:** 14233 chờ transaction 515922 (của 14227); 14227 chờ transaction 515923 (của 14233). Mỗi bên giữ khóa dòng mà bên kia cần.
2. **Ai bị hủy:** tiến trình 14233 (log ghi `ERROR` ở PID 14233). Postgres hủy tiến trình phát hiện vòng sau `deadlock_timeout` (1 giây mặc định), không phải bên "đến sau" hay "ít việc hơn".
3. **Tài nguyên:** dòng `(0,1)` của `p08.acct` (CONTEXT) và dòng id=2. "ShareLock on transaction" là cách Postgres chờ một transaction kết thúc (lock dòng thực chất đặt trên xid).
4. **Nguyên nhân:** hai luồng chuyển tiền ngược chiều (1→2 và 2→1) lấy khóa theo thứ tự `from` rồi `to`.
5. **Sửa:** khóa mọi dòng cần dùng theo một thứ tự toàn cục (tăng dần theo `id`) trước khi sửa (`SELECT … WHERE id IN (…) ORDER BY id FOR UPDATE`); khi đó B chờ A ngay ở lệnh đầu tiên mà không giữ gì, nên không có vòng. Sau sửa check ex03 đạt, cả hai lần chuyển commit.
6. **Phòng thủ thêm:** ứng dụng vẫn nên retry khi gặp `40P01` (có thể còn deadlock do các đường mã khác); `log_lock_waits = on` để thấy cả những lần chờ chưa thành deadlock; `deadlock_timeout` đừng hạ quá thấp (kiểm tra deadlock tốn CPU).
