# P10a · ex05 📏 Tràn bộ nhớ: sort và hash

Đo `SELECT count(*) FROM (SELECT id FROM T ORDER BY amount, id) s` (sort) và `SELECT count(*) FROM (SELECT u, count(*) FROM T GROUP BY u) s` với `SET enable_sort = off; enable_indexscan = off; enable_indexonlyscan = off` (ép HashAggregate), parallel tắt, 3 lần/ô lấy nhanh nhất, Postgres 18.6, cache ấm. `temp` = `Temp Written Blocks` (1 block = 8 kB).

| thí nghiệm | scale | `work_mem` 4MB | 64MB | 1GB |
|---|---|---|---|---|
| Sort `amount, id` | s (10k) | 4.1 ms · temp 0 | 3.8 ms · 0 | 3.8 ms · 0 |
| | m (1M) | **553 ms** · temp **6 675** | 707 ms · 0 | 692 ms · 0 |
| | l (10M) | **6 273 ms** · temp **132 477** | 7 081 ms · temp 66 078 | 8 609 ms · 0 |
| HashAggregate `GROUP BY u` | s | 6.1 ms · 0 | 4.0 ms · 0 | 3.6 ms · 0 |
| | m | **559 ms** · temp **10 938** | 600 ms · 0 | 590 ms · 0 |
| | l | **4 684 ms** · temp **136 329** | 5 311 ms · 0 | 5 025 ms · 0 |

## Giải thích
- **Tràn xảy ra đúng chỗ dự đoán:** ở `s` không bao giờ tràn. Ở `m` sort cần 46 MB (ex04) nên 4 MB tràn (6 675 page ≈ 52 MB); ở `l` sort cần cỡ 10× (suy ra ≈ 460 MB, chưa đo ngưỡng chính xác) nên 64 MB vẫn tràn (66 078 page) và chỉ 1 GB đủ. HashAggregate với 1M nhóm tràn ở 4 MB (10 938 page) và vừa ở 64 MB; ở `l` số nhóm của `u` vẫn chỉ 1 000 000 (cột `u` chỉ có 1M giá trị khác nhau) nên 64 MB đã đủ (temp 0), dù đọc 10× số dòng: bộ nhớ của hash aggregate theo **số nhóm**, bộ nhớ của sort theo **số dòng**.
- **Tràn tốn I/O nhưng không chậm hơn trong môi trường này:** sort tràn (4 MB) lại nhanh hơn sort trong RAM (1 GB) ở `l`: 6.27 s so với 8.61 s; hash tràn 4.68 s so với 5.03 s. Ghi 132 477 page (≈ 1 GB) vào file tạm chỉ tốn vài trăm ms vì SSD và page cache của OS rất nhanh; trong khi đó cấu trúc nhỏ (4 MB) vừa với cache CPU nên xử lý mỗi dòng nhanh hơn. Đây là **giả thuyết giải thích (chưa kiểm chứng bằng profiler)**; số đo thì chắc chắn.
- **Kết luận thực hành:** đừng tăng `work_mem` toàn cục chỉ vì thấy `Sort Method: external merge`. Spill là tín hiệu "plan này cần nhiều bộ nhớ", không phải bằng chứng "chậm". Đo thời gian thật trước và sau. `work_mem` nhân theo số node sort/hash và số kết nối (4 MB × 100 kết nối × vài node), nên tăng bừa có thể hết RAM. Trên đĩa chậm hoặc máy đang bận I/O, sort tràn sẽ chậm hơn rõ rệt; phép đo này chỉ đúng cho môi trường có page cache lớn.
