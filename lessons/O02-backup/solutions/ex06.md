# O02 · ex06 🔴 "Có backup nhưng chưa ai thử restore"

Câu chuyện: kiểm toán hỏi *"Bao lâu bạn thử restore một lần? Backup đêm qua có dùng được không?"* Một bản backup chưa từng restore thử chỉ là hy vọng.

## Phần đo được
```bash
docker exec sql-practice-pg pg_basebackup -U postgres -D /tmp/bb -Fp -X stream -c fast   # 6.2 s, 993 MB cho cả cluster 977 MB
docker exec sql-practice-pg pg_verifybackup /tmp/bb                                       # 0.35 s → "backup successfully verified"
# phá một byte trong file điều khiển, kiểm tra lại:
docker exec sql-practice-pg pg_verifybackup /tmp/bb
# → pg_verifybackup: error: /tmp/bb/global/pg_control: CRC is incorrect
```
- `pg_verifybackup` kiểm tra file nào thiếu/thừa/sai checksum theo `backup_manifest` và WAL cần thiết có mặt không: bắt được hỏng ở mức **file**, rất rẻ (0.35 s cho ≈ 1 GB).
- Nó **không** chứng minh dữ liệu đọc được và khởi động được: chỉ restore thử thật mới kết luận.

## Runbook kiểm thử restore tối thiểu (đề xuất)
1. Tự động hóa, chạy định kỳ (hằng tuần là điểm khởi đầu hợp lý) trên máy riêng: lấy backup mới nhất → restore (base + WAL tới một thời điểm xác định, hoặc `pg_restore`) → khởi động → chạy bộ kiểm tra.
2. Bộ kiểm tra: `count(*)` các bảng chính so với số ghi nhận lúc backup; `sum(total_amount)` hoặc checksum một vài bảng; một truy vấn nghiệp vụ mẫu; `pg_amcheck` trên index quan trọng.
3. Ghi lại **RTO đo được** (thời gian restore thực tế) và **RPO** (tuổi của dữ liệu mới nhất khôi phục được: với dump = khoảng giữa hai lần dump; với WAL archiving = phần WAL chưa archive, ≤ `archive_timeout` cộng độ trễ lưu trữ).
4. Cảnh báo khi: backup thất bại, `pg_stat_archiver.failed_count` tăng, `pg_verifybackup` lỗi, thử restore thất bại, hoặc kích thước backup lệch bất thường.

Phần 1, 2, 4 là thiết kế (đề xuất), phần đo được ở trên là số thật.
