# O02 · ex05 🔴 "Dev xóa nhầm 299 900 dòng lúc 14:03, khôi phục về 14:02:50"

Chạy bằng `bash lessons/O02-backup/pitr-lab.sh <up|base|oops|restore|down>` (đã chạy end-to-end trên Postgres 18.6 trong Docker; không đụng DB bài tập).

## Trình tự và số đo thật
1. `up`: Postgres nguồn bật `wal_level=replica`, `archive_mode=on`, `archive_command='test ! -f /archive/%f && cp %p /archive/%f'`, `archive_timeout=30`. Tạo `orders_demo` 200 000 dòng.
2. `base`: `pg_basebackup -D /archive/base -Fp -X stream -c fast` → **0.49 s**, 52 MB (cho DB ~37 MB dữ liệu cộng WAL). `pg_verifybackup` → `backup successfully verified`.
3. `oops`: chèn thêm 100 000 dòng (lên 300 000), ghi **T1** = `2026-10-18 02:06:56.43+00` (thời điểm tốt), 3 giây sau `DELETE FROM orders_demo WHERE id > 100` (xóa 299 900 dòng), ghi T2, `pg_switch_wal()` để đoạn WAL cuối được lưu. Bảng còn 100 dòng.
4. `restore "<T1>"`: copy base backup vào volume mới, thêm vào `postgresql.auto.conf`:
   ```
   restore_command = 'cp /archive/%f %p'
   recovery_target_time = '<T1>'
   recovery_target_action = 'promote'
   ```
   và `touch recovery.signal`, khởi động Postgres. Log: `starting point-in-time recovery to 2026-10-18 02:06:56.43+00` → `restored log file … from archive` → `recovery stopping before commit of transaction 756, time 02:06:59.70` (đúng giao dịch DELETE) → `archive recovery complete`. Kết quả: **300 000 dòng, max(id) = 300000**. Tổng thời gian từ `docker run` đến khi nhận kết nối ghi: **≈ 2.3 s**, replay mất 0.49 s cho ≈ 56 MB WAL (lần chạy thủ công ban đầu cho cùng kết quả).

## Giải thích
- **Hai nguyên liệu**: (a) base backup (bản sao vật lý nhất quán), (b) chuỗi WAL liên tục từ lúc backup tới thời điểm đích. Thiếu một đoạn WAL → recovery dừng sớm ở chỗ thiếu.
- `recovery_target_time` dừng **trước** giao dịch đầu tiên có commit sau thời điểm đích (`recovery_target_inclusive` mặc định `on`: gồm cả giao dịch commit đúng thời điểm đó). Chọn thời điểm bằng cách đọc log/audit; nếu chọn sai, restore lại từ base (mỗi lần thử vài giây ở quy mô này).
- `recovery_target_action = 'promote'`: xong là mở ghi luôn (timeline mới). Muốn xem trước khi quyết định dùng `pause`.
- `archive_timeout` ép chuyển file WAL sau tối đa N giây ngay cả khi ít ghi: nó quyết định **RPO** trong trường hợp mất ổ đĩa (dữ liệu sau file WAL cuối cùng chưa lưu thì mất). WAL chưa archive nằm trên đĩa nguồn.
- `archive_command` phải trả 0 chỉ khi file đã nằm an toàn; `test ! -f … && cp` tránh ghi đè. Trên production archive ra nơi **khác máy** (object storage, NFS); công cụ như pgBackRest/WAL-G làm việc này kèm nén, mã hóa, lưu giữ.
- Thực tế bạn không bao giờ restore đè lên server đang chạy: dựng instance khôi phục riêng, xác minh, rồi lấy lại đúng dữ liệu cần (ex04) hoặc chuyển traffic.
