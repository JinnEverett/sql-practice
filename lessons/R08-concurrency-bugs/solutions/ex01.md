# R08 · ex01 · Tái hiện lost update

Chạy `solutions/ex01.sql` (tự dựng hai session bằng `dblink`, không cần mở cửa sổ thứ hai). Kết quả thật (Postgres 18.6):

| cách | thao tác của hai session | `n` sau khi cả hai cộng 1 từ `n = 0` |
|---|---|---|
| **Sai**: đọc `n`, tính `n + 1` ở phía ứng dụng, ghi lại `SET n = <số đã tính>` | A và B cùng đọc `n = 0`; A ghi 1 rồi commit; B ghi 1 rồi commit | **1** (mất một lần cộng) |
| **Đúng**: `UPDATE … SET n = n + 1` | A cập nhật chưa commit; B bị chặn chờ khóa dòng; A commit; B đọc phiên bản dòng MỚI NHẤT (`n = 1`) rồi ghi 2 | **2** |

## Giải thích
- Ở `READ COMMITTED` (mặc định), mỗi **câu lệnh** thấy snapshot riêng. Hai câu `SELECT n` đều thấy 0 vì không giao dịch nào commit lúc đó; việc "tính n + 1" diễn ra ngoài database nên Postgres không biết hai giá trị 1 kia lẽ ra phải là 1 và 2. Đây là **lost update**.
- Với `UPDATE … SET n = n + 1`, khi B gặp dòng đang bị A khóa, B **chờ**. Khi A commit, Postgres tính lại biểu thức `n + 1` trên phiên bản dòng mới của A (cơ chế EvalPlanQual trong `READ COMMITTED`). Phép toán nằm trong database nên không có khoảng hở giữa đọc và ghi.
- Quy tắc: logic "đọc rồi quyết định rồi ghi" phải nằm trong **một câu lệnh** (atomic update với điều kiện ở `WHERE`), hoặc được bảo vệ bằng khóa (`SELECT … FOR UPDATE`), hoặc bằng kiểm tra phiên bản (optimistic locking, ex03), hoặc chạy ở `SERIALIZABLE` kèm retry (ex07).
- `REPEATABLE READ` không tự chặn kịch bản này theo cách mà bạn mong: nếu B chạy `SET n = n + 1` ở `REPEATABLE READ` và dòng đã bị A sửa sau snapshot của B, B nhận lỗi `could not serialize access due to concurrent update` (40001) thay vì mất dữ liệu; ứng dụng phải retry.
